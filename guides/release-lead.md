# Инструкция Выпускающему

Для человека в роли Выпускающего шаблона IWE и для его ИИ-агента. Роль и её метод — в Паке: [DP.ROLE.120 «Выпускающий»](https://github.com/MimEcoSys/PACK-digital-platform/blob/main/pack/digital-platform/02-domain-entities/DP.ROLE.120-release-issuer.md); все этапы и роли выпуска — в [листе этапов](release-process.md). Здесь — что делаешь ты, по шагам, и какие решения за тобой.

**Главное.** Ты решаешь, что и когда получают пользователи, и выпускаешь ровно ту сборку, которую проверили. Код ты не пишешь и не чинишь: это делает Разработчик. Твои инструменты — форма решений выпуска, кнопки GitHub и тема выпуска в Зулипе.

**Агенту Выпускающего.** Ты помощник, не Выпускающий: готовишь, показываешь, напоминаешь и проверяешь программами. Решения (состав, блокирующие строки, принятие оговорок, «режем», слияние, откат) — только словами человека. Сообщение в Зулип или комментарий от его имени — только после того, как он одобрил текст. Пиши только в его файл роли: `releases/<N>/decisions.md` (правило в [CLAUDE.md](../CLAUDE.md)).

## Что нужно один раз

- Аккаунт GitHub в организации MimEcoSys, команда `iwe-release-lead`, и права в репозитории шаблона на запуск Actions и слияние.
- Копия этого репозитория у себя: `git clone https://github.com/MimEcoSys/DS-iwe-releases`.
- Доступ к Зулипу МИМ, тема выпуска «Выпуск <N>».

## Шаги выпуска

Номера этапов — из [листа этапов](release-process.md).

### 1. Подготовка формы решений (до нарезки)

Открой `releases/<N>/README.md` (с чего начать) и `releases/<N>/candidates.md` (кандидаты с рекомендацией Разработчика). Заполни в `releases/<N>/decisions.md`:

| Строка | Что решить | Подсказка |
|---|---|---|
| Состав: что взято / отложено | какие кандидаты идут в выпуск | «всё после прошлого выпуска» — допустимый ответ; неразделимые группы берутся целиком |
| Предел числа правок | сколько максимум | меньше правок — меньше риск |
| Какие строки проверки блокируют | по протоколу `releases/<N>/protocol.md` | колонка «Блокирует» — предложение Разработчика, решаешь ты |
| Обещает ли выпуск работу в Windows | да / нет | «да» — нужен тестировщик с Windows |
| Тестировщики | логины GitHub | назначь, раздай [инструкцию](tester-macos.md) и номера строк |
| Кто исполняет роли | все роли из листа этапов | и честно — где независимости нет |
| Окно наблюдения, порог отката | сколько дней смотреть; какие обращения серьёзны | например, 7 дней; «обновление ломает установку» — серьёзно |

Проверка: `python3 ops/check_decisions.py` — без замечаний.

### 2. «Режем» (этап 1)

Скажи Разработчику «режем». Снимок — вершина основной ветки шаблона в этот момент. Разработчик запускает нарезку и присылает ссылку на запрос на слияние ветки выпуска. Впиши в форму строку «Версия основной ветки в момент «режем»».

### 3. Отбор на ветке выпуска (этапы 2–3)

Разработчик дописывает поля и коды записей. Отложенное ты называешь, Разработчик снимает его откатом на ветке выпуска — не в основной. Основную ветку до слияния не двигают; если сдвинулась — Разработчик вливает её в ветку выпуска, и проверка начинается заново.

### 4. Кандидат (этап 4)

Разработчик ставит метку `v<N>-rc.<K>` и пишет в запросе дерево кандидата. Раздай номер тестировщикам и проверяющему red team.

### 5. Проверка (этапы 5–9)

Ждёшь отчёты: программы, рецензия, аудит кода, отметки тестировщиков, вердикт red team. Агент собирает их в одну сводку: что пройдено, что нет, кто что сказал.

### 6. Решения по находкам (этап 10)

По каждой находке — одно из трёх:
- **чинить** — Разработчик исправляет на ветке выпуска, новый кандидат, все строки заново;
- **принять оговорку** — она идёт в анонс, твой логин — в `accepted_by`;
- **отложить кандидата** — снять из состава откатом на ветке выпуска.

Вердикт red team `BLOCKED` или `cannot_verify` — не выпускать. `CAUTION` — только с принятыми тобой оговорками. «Нет» Рецензента выпуска можно переопределить, но причину запиши в форму.

### 7. Согласование (этапы 11–12)

Агент готовит итог для темы выпуска в Зулипе, ты одобряешь текст, он уходит. Твой ответ «согласовано» в теме — ссылка на него идёт в форму. Заполни строку «Итог: выпускаем / откладываем».

### 8. Слияние (этап 13)

Перед кнопкой — две проверки (агент запускает, ты смотришь вывод):

```bash
# в шаблоне, на ветке выпуска
bash scripts/check-release-branch-base.sh <N> origin --head
# здесь
python3 ops/check_decisions.py --require-final --rc-tree <дерево последнего кандидата>
```

Обе без замечаний → в запросе на слияние ветки выпуска: **Approve workflows to run**, дождаться зелёной проверки `Validate Template`, затем **Merge**. Выпуск поставит программа, только если содержимое совпало с проверенным кандидатом; иначе остановится — тогда разбираться с Разработчиком, не обходить.

### 9. После выхода (этап 14)

Напоминание о проверке опубликованного выпуска создаётся само — пройди его. В окне наблюдения смотри обращения; серьёзное по порогу — решение об откате за тобой. Вердикт red team Разработчик переносит в журнал шаблона отдельным запросом.

## Чего не делать

- Не выпускать сборку, которую не проверили: любая правка после кандидата — новый кандидат.
- Не принимать решение за отсутствующего тестировщика: «не проверялось» — это «не пройдено», если строка блокирующая.
- Не обходить проверки программ и не просить агента «пропустить».
