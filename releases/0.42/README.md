# Выпуск 0.42: что взять и что сделать

Подготовил Разработчик. Здесь всё про выпуск 0.42: что это за выпуск, где что лежит, что уже сделано и что сделать по шагам. Решает Выпускающий. Если ты здесь впервые — сначала [с чего начать](../../guides/release-lead-start.md); общий порядок любого выпуска — [этапы, роли, методы](../../guides/release-process.md) и [шаги Выпускающего](../../guides/release-lead.md). Ниже — то же самое, но с конкретными значениями 0.42.

## Что за выпуск

- **0.42.0** — первый выпуск шаблона через проверенную сборку-кандидат (`v0.42.0-rc.<K>`), а не автоматический недельный. Тип — минорный.
- **Основа** — прошлый выпуск **0.41.11**. Пользователи на 0.41.11 получат всё, что влито после него и взято в состав. Кто ещё на 0.36, получит и изменения 0.37–0.41.11 (по данным Разработчика на 04.11 — 4 из 15 пользователей).
- **Обещание** — стабильный выпуск: входит только проверенное. Не прошедшее проверку снимается с ветки выпуска, основная ветка шаблона остаётся как есть.
- **Ведёт** — пока назначенный Выпускающий роль не принял, выпуск 0.42 ведёт владелец репозитория (решение 10.11.2026). Кто исполняет остальные роли — строка «Кто исполняет роли» в [форме решений](decisions.md).

## Что уже сделано (на 10.11)

- **Механика выпуска готова.** Нарезка берёт только вершину основной ветки; метка кандидата не ставится без полей у записей и если основная ветка сдвинулась после нарезки; выпуск без кандидата и с содержимым, отличным от последнего кандидата, останавливается; ручной выпуск не публикует коммит вне основной ветки ([FMT #1508](https://github.com/TserenTserenov/FMT-exocortex-template/pull/1508), [#1512](https://github.com/TserenTserenov/FMT-exocortex-template/pull/1512), [#1516](https://github.com/TserenTserenov/FMT-exocortex-template/pull/1516), [#1520](https://github.com/TserenTserenov/FMT-exocortex-template/pull/1520)).
- **Возврат на 0.41.11** распознаётся по версии установленного манифеста и без подтверждения ничего не меняет (#1520).
- **Навык обновления** объясняет изменения по метке кандидата, а не по основной ветке (#1516).
- **Протокол проверки, форма решений, проверка программой** с итоговым режимом перед слиянием — здесь, `ops/check_decisions.py`.
- **В основной ветке после 0.41.11** — 63 слияния (на 10.11), в том числе навык поиска метода (`/find-method`, код Ц49-12) и лёгкий онбординг 1.0.2.
- **Кандидат rc.1** — метка `v0.42.0-rc.1` (fc484854, 11.11), у всех 81 записи раздела 0.42.0 четыре поля (FMT #1525, #1526).
- **Список кандидатов пересобран 11.11** по снимку «режем» 637e06a1: 81 правка, у каждой связь с кодом из поля «Цель · Результат» и черновик Разработчика (риск, рекомендация, как откатить).

## Что ещё не готово

- **Защита меток выпуска `v*` в шаблоне не включена.** Это настройка GitHub у владельца шаблона: правило для меток `v*` — создавать и удалять только владельцу и программе выпуска.
- **Тестировщики:** macOS назначен (логин уточняется); Windows и Linux — нет. [Инструкция тестировщику](../../guides/tester-macos.md) — черновик, Разработчик проходит её сам на rc.1 до передачи.
- **Форма решений** заполнена только в строке «Кто исполняет роли».
- **Права Выпускающего в шаблоне.** Шаблон принадлежит личному аккаунту владельца; новому Выпускающему нужны права соавтора там (запуск проверок, слияние) — их даёт владелец.

## Шаги выпуска 0.42

### Шаг 1. Решения до нарезки — Выпускающий

Заполни [форму решений](decisions.md). Предложения Разработчика — в скобках, решаешь ты:

1. **Состав: что взято / отложено** (взять всё после 0.41.11, отложенного нет; запрос #1504 — фоновые роли на DeepSeek — не слит и в состав не входит).
2. **Предел числа правок** (без предела: состав уже зафиксирован основной веткой).
3. **Какие строки проверки блокируют** (колонка «Блокирует» в [протоколе](protocol.md); строку 16 для Claude Desktop и ChatGPT — решить).
4. **Обещает ли 0.42 Windows** (нет, пока нет тестировщика с Windows; тогда строки 6–7 не блокируют).
5. **Тестировщики** — логины.
6. **Окно наблюдения и порог отката** (7 дней; серьёзно — обновление ломает установку, пропадают свои правки пользователя, агент не открывает день).
7. **Нужны ли записям-документации поля «как проверить» и «как откатить»** (нужны: программа шаблона их уже требует у всех записей).

Проверка: `python3 ops/check_decisions.py` — без замечаний.

### Шаг 2. «Режем» — Выпускающий говорит, Разработчик запускает

Разработчик: пересобирает кандидатов, проверяет, что общая проверка шаблона на вершине основной ветки зелёная, и запускает **Release Candidate**: `mode=cut`, `snapshot_sha=<полный SHA вершины main>`, `release_type=minor`. Результат — ветка `release/v0.42.0` и запрос на слияние в основную. Выпускающий вписывает SHA в строку «Версия основной ветки в момент «режем»».

С этого момента основную ветку шаблона до слияния выпуска не двигают. Сдвинули — Разработчик вливает её в ветку выпуска, и проверка начинается заново.

### Шаг 3. Поля, коды и отбор — Разработчик, Разметчик кодов

На ветке выпуска у каждой записи раздела 0.42.0 списка изменений: «Цель · Результат», «Как проверить», «Как откатить» (на 10.11 — около 78 записей, поле есть у 11). Отложенное Выпускающим снимается откатом на ветке выпуска ([как откатывать](candidates.md#как-откатывать)).

### Шаг 4. Кандидат rc.1 — Разработчик

**Release Candidate**: `mode=next-rc`, `version=0.42.0`. Метка `v0.42.0-rc.1` и дерево кандидата — в комментарии запроса на слияние. Выпускающий раздаёт номер кандидата исполнителям.

### Шаг 6. Находки — Выпускающий

По каждой: чинить (новый кандидат), принять оговорку (в анонс, твой логин в `accepted_by`) или отложить правку (откат на ветке выпуска). Вердикт red team `BLOCKED` или `cannot_verify` — не выпускать; `CAUTION` — только с принятыми тобой оговорками.

### Шаг 7. Согласование — Выпускающий

Итог проверки уходит в тему «Выпуск 0.42» после твоего одобрения текста; твой ответ «согласовано» в теме — ссылка на него в `accepted_by` и строку «Итог» формы решений.

### Шаг 8. Слияние — Выпускающий

```bash
# в шаблоне, на ветке release/v0.42.0
bash scripts/check-release-branch-base.sh 0.42.0 origin --head
# здесь
python3 ops/check_decisions.py --require-final --rc-tree <дерево последнего кандидата>
```

Обе без замечаний → в запросе на слияние ветки выпуска: **Approve workflows to run**, дождаться зелёной `Validate Template`, затем **Merge**. Программа выпуска поставит метку `v0.42.0` и выпуск, только если содержимое совпадает с последним кандидатом.

### Шаг 9. После выхода — Выпускающий

Пройти напоминание о проверке опубликованного выпуска (создаётся само). Окно наблюдения — по форме решений; серьёзное обращение по порогу — решение об откате. Разбор выпуска — абзацем в конце формы решений ([как](../../guides/release-lead-training.md#разбор-после-каждого-выпуска)).

## Как отложить уже влитое

Все кандидаты уже в основной ветке шаблона. Ветка выпуска делается от основной в момент «режем», поэтому отложить кандидата — значит снять его откатом на ветке выпуска, до метки кандидата. Ветка выпуска потом вливается в основную, поэтому отложенное исчезнет и оттуда; вернуть его в следующий выпуск — откатить сам откат. Порядок и что делать с конфликтами — на [странице кандидатов](candidates.md#как-откатывать).

## Словарь

| Слово | Что значит |
|---|---|
| сборка-кандидат (rc) | проверяемая сборка будущего выпуска; выходит ровно та, что прошла проверку |
| ветка выпуска | ветка шаблона, на которой собирают выпуск; делается от основной ветки в момент «режем» |
| дерево кандидата | отпечаток содержимого сборки (40 символов); по нему видно, что проверяли именно её |
| слияние | влитый в основную ветку запрос на слияние (PR, номер `#NNNN`) |
| откат | коммит, который снимает изменения другого коммита (`git revert`) |
| red team | независимая атака на сборку: попытка её сломать до выхода |
| репетиция, пробный прогон | режим проверки установки, в котором агенту запрещено что-либо записывать; одно и то же |
| защита, хук, гейт | программа, которая проверяет каждое действие ИИ-агента и может его запретить |
| разборщик | фоновая роль шаблона, которая разбирает заметки и извлекает из них знания |
| Кими | второй ИИ-агент, с которым может работать среда IWE |
| РП | рабочий продукт — единица работы Разработчика |
| «Ц84-04» | код обещанного результата: цель 84, результат 04 |
| «служебное» | у правки нет видимого пользователю результата |
