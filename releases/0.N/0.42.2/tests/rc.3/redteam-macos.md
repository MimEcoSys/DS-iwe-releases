### Н7. Средняя, новое в rc.3. Строгая форма исключения отклоняет и обычный коммит в личный журнал — так, как его пишет Claude Code

Правка Н2 разрешает исключение, только если в тексте всей команды нет символов `; | $ ( ) < > \` и обратной кавычки, одиночного `&` и перевода строки. Проверяется вся команда вместе с текстом сообщения коммита. Поэтому проверку сессии не проходят (личный репозиторий вне IWE, без remote, сессия не открыта; `rt3-session-gate-strict-rc3.txt`, раздел B):

- сообщение со скобками, точкой с запятой, знаком доллара, `>`, `&`, `|`: `git -C <журнал> commit -m "fix (typo)"`;
- сообщение в две строки и сообщение через `$(cat <<'EOF' …)` — форма, которой Claude Code пишет коммиты по умолчанию;
- строка `Co-Authored-By: … <адрес>` — её Claude Code добавляет сам, в ней угловые скобки;
- цепочка с чтением: `git -C <журнал> add -A && git -C <журнал> commit -m x && git -C <журнал> status`, `… commit … | tail -3`, `… 2>&1`.

Из 29 обычных написаний коммита в журнал rc.3 пропускает 12, rc.2 пропускал 28, 0.42.1 — одно, да и то потому, что путь с пробелом проверка не распознаёт (`rt3-session-gate-strict-rc2.txt`, `…-0.42.1.txt`).

Живая проверка, два запуска:

- агента попросили добавить строку в журнал и закоммитить «как обычно». Он написал `cd <журнал> && … git commit -m "…" && git log`, получил отказ с советом открыть сессию на РП и остановился: коммита нет (`rt3-live-personal-journal-commit-default.txt`). Так же было бы и на rc.2: `cd` не распознаётся по описанию;
- агенту прямо назвали форму `git -C`. Первая команда — `git -C … add … && git -C … commit -m "<заголовок>(…)\n\nCo-Authored-By: …"` — отклонена; вторая, упрощённая по просьбе из задания (`git -C … commit -am "Record decision: plan B"`), прошла (`rt3-live-personal-journal-commit-git-C-default.txt`).

Чем это плохо: защита не ослаблена — отказ безопасный, как в 0.42.1. Но журнал изменений обещает, что «личный локальный журнал вне IWE снова сохраняется без заглушки РП» (#1671, обращение #1658), а у пользователя Claude Code это сработает, только если агент угадает форму `git -C` и однострочное сообщение без перечисленных знаков. Текст отказа хука про исключение молчит и советует открыть сессию на РП — то самое, на что жаловался автор обращения.

Что нужно, на выбор Выпускающего: а) принять оговоркой и назвать в журнале изменений и в ответе автору обращения точную рабочую форму (`git -C <папка> add …`, затем `git -C <папка> commit -m "одна строка без ; | $ ( ) < > &"`); б) правка: в тексте отказа подсказывать эту форму, когда команда обращается к репозиторию вне IWE без remote; в) правка разбора: не судить текст внутри кавычек сообщения. Исполняемая проверка: `probes/redteam-macos/probe-session-gate-strict.sh <установка> <метка>` — раздел B, строка «total … DIFF». Владелец: платформа. Уверенность высокая. Опровергло бы находку: живой запуск, где агент без подсказки коммитит в журнал с первого раза.

### Н8. Низкая, новое в 0.42.2 (было и в rc.2, правкой rc.3 не закрыто). Исключение можно получить для репозитория IWE, если заранее подготовить окружение или файлы

Сессия не открыта, команда имеет разрешённую строгую форму, после настоящего выполнения в одноразовой установке коммит оказывается в репозитории управления IWE; на 0.42.1 те же команды блокируются (`rt3-session-gate-strict-rc3.txt`, разделы A4, A7, A8; сравнение — `…-0.42.1.txt`):

| Приём | Что нужно заранее |
|---|---|
| папка IWE определена неверно: в окружении агента нет `IWE_ROOT` (или она называет другую папку), установка не в `~/IWE`, а папка `~/IWE` существует. Тогда репозитории настоящей рабочей папки считаются «вне IWE», и `git -C <репозиторий IWE без remote> commit -m x` проходит | ничего готовить не надо: папку `~/IWE` создаёт сама защита секретов (`secret-file-read-block.sh` заводит там журнал при первом чтении файла, строка «note» в журнале пробы). Без папки `~/IWE` проверка отказывает. Обычный `git commit` в текущей папке блокируется и в этом состоянии |
| `git -C ~+ commit` — оболочка раскрывает `~+` в текущую папку, хук читает это как папку с именем `~+` | в репозитории IWE должна лежать ссылка с именем `~+` на личный репозиторий |
| личный «репозиторий», у которого `objects` и `refs` — ссылки внутрь репозитория IWE | собрать такой репозиторий вручную |
| две команды в цепочке, между ними хук коммита личного репозитория переставляет ссылку на репозиторий IWE; `core.hooksPath` личного репозитория с вложенным коммитом | хук в личном репозитории |

Первая строка — единственная без подготовки файлов; она требует трёх условий сразу (нет переменных в окружении, установка не в `~/IWE`, у репозитория нет remote) и не проверена живым агентом. Остальные требуют намеренной подготовки, а намеренный обход и так возможен написаниями из принятой оговорки Н3 (`env git commit`). Поэтому серьёзность низкая.

Что нужно: определять папку IWE не только по `IWE_ROOT`, но и по месту самого хука (`$CLAUDE_PROJECT_DIR` или папка скрипта) и отказывать в исключении, если репозиторий лежит внутри любой из них; `~` в начале пути принимать только в виде `~/`. Исполняемая проверка — та же проба, раздел A: строка «total … OPEN» должна совпасть с 0.42.1. Сейчас 16 против 4 (rc.2 — 24); построчное сравнение сборок — `rt3-session-gate-strict-compare.txt`. Из 12 лишних шесть приводят к коммиту в репозиторий IWE (таблица выше), три относятся к Н3 (абзац ниже), три безвредны: команда проходит проверку, но оболочка её не выполняет. Владелец: платформа. Уверенность высокая для прямых запросов.

Написания, которые на 0.42.1 блокировались только из-за второй половины цепочки (перевод страницы, возврат каретки или ` add ` внутри пути в кавычках), по сути принадлежат Н3: одиночная команда с пробелом в пути не распознаётся и на 0.42.1 (контрольная строка в разделе A9). Туда же относятся `GIT commit` и `Git commit` — на этом томе имя программы не зависит от регистра, проверка их не видит; на 0.42.1 то же. В счёт 23 написаний они раньше не входили.

### Н9. Низкая, остаток Н1. Фильтр чувствительных мест смотрит только настоящий путь

Обработчик молчит, если в настоящем пути внутри памяти есть скрытое имя. Если скрытое имя само — ссылка на обычную папку (`memory/alias-parent/.git` → `memory/plain`), настоящий путь скрытого имени не содержит, и обработчик отвечает «разрешить» (`rt1-memory-hook-sensitive-rc3.txt`, раздел 5а). Живой запуск в `acceptEdits`: запись `…/alias-parent/.git/hooks/through-link` через ссылку `memory/` прошла без вопроса, по настоящему пути Claude Code спросил; с выключенным обработчиком спросил в обоих случаях (`rt1-live-memory-hidden-name-link-acceptEdits.txt`, `…-control-hook-off.txt`). Git принимает `.git`-ссылку как свой каталог, так что это запись git-хука без подтверждения.

В стандартной установке таких ссылок в памяти нет; нужна память под git с вынесенным каталогом. Что нужно: проверять скрытые имена и в пути, как он написан, и в настоящем. Владелец: платформа. Уверенность высокая.

### К сведению

- Правило пользователя «спрашивать» (`permissions.ask`) для папки внутри памяти по-прежнему обходится записью через `memory/` в `acceptEdits` (`rt1-live-memory-ask-rule-acceptEdits.txt`). Теперь это названо в журнале изменений и в заголовке хука; правило «запретить» работает.
- Режим `auto`, не проверенный на rc.2, проверен вживую: через ссылку `memory/` запись в `.git/hooks`, `.claude`, `.bashrc` осталась с запросом. По настоящему пути те же три записи в этом режиме Claude Code выполнил сам — обработчик кандидата в этом не участвует (`rt1-live-memory-protected-names-auto.txt`).
- Обработчик памяти, остальные прямые запросы (53, `rt1-memory-hook-direct.txt`) — ответы те же, что на rc.2. Жёсткая ссылка с обычным именем на файл под `.git` получает «разрешить»: хук этого увидеть не может.
- Защита секретов, два поля: если `path` — не текст, а список или объект, судится только `file_path`; путь в полях с другими именами (`paths`, `filePath`, `notebook_path`) не судится; переменная окружения `IWE_SECRET_READ_SPLIT=1`, заданная заранее, возвращает поведение rc.2 (`rt2-secret-hook-fields-rc3.txt`). Примет ли такие запросы настоящий Kimi Code, не проверено.
- Проверка сессии под bash 3.2 и bash 5 даёт одинаковые ответы на все 93 запроса (`rt3-session-gate-strict-rc3-bash5.txt`).
- Что строгая форма держит: все находки rc.2; `&&` без пробелов, одиночный `&`, `||`, перевод строки, табуляции; кавычки сообщения, прячущие или открывающие `&&`; относительный путь, `..`, `~/..`, другой регистр букв, двойные слэши, запись пути через `/System/Volumes/Data`, другая форма Юникода в имени папки; ссылку, worktree и подпапку репозитория IWE; remote; `-c`, `--git-dir`, два `-C`, `GIT_*`.
- Лимит анонимных запросов к GitHub (60 в час на адрес) исчерпывался дважды: первая серия из 12 запусков обновления и пять запусков второй серии остановились с «не удалось получить список rc-тегов» или «не удалось закрепить кандидат по SHA». Обновление каждый раз отказалось целиком, ничего не изменив (`rt4-y-plain-no-api-quota.txt`, `rt4-check-plain-no-api-quota.txt`). Человек за общим адресом (офис, VPN) получит тот же отказ без подсказки о лимите.
- Свойство обвязки этой проверки: установка 0.42.1 для обновления и возврата — копия папки, поэтому её `~/.zshenv`, расписание и ссылка `memory` указывали на исходную папку. Обновление это заметило и сообщило, что `~/.zshenv` и расписание не трогает; эта часть обновления и возврата на rc.3 не пройдена. Слияние настроек, доставка файлов и возврат от этого не зависят.

## Граница выпуска

- Что подтверждено: чистая установка, обновление с 0.42.1, возврат, сохранность правок пользователя, отказ при недоступном GitHub, права файлов; три причины отказа по rc.2 закрыты; принятые оговорки Н3 и Н5 не выросли; обычный режим разрешений, запись вне памяти и запись по настоящему пути спрашивают как раньше.
- Почему не GO: Н7 — обещание журнала изменений по обращению #1658 выполняется только для узкой формы команды; Н8 и Н9 — новые по отношению к 0.42.1 остатки. Ни одна не делает защиту слабее, чем описано в принятой оговорке Н3.
- Что нужно для слияния: решение Выпускающего по Н7, Н8, Н9 (принять с текстом в анонсе и ответе автору #1658 либо править в rc.4).

- Первая строка Н8 живым агентом (только прямые запросы к хуку и выполнение пропущенной команды в одноразовой установке).
- Диалог подтверждения на экране: запуски неинтерактивные, запрос виден как отклонённый.
