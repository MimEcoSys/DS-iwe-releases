### Н1. Средняя, новое в rc.2. Обработчик памяти отвечает «разрешить» и там, где подтверждение спросил не переход по ссылке

Хук `memory-write-permission.sh` (#1626) не видит причину запроса. Поэтому в режимах `acceptEdits` и `auto` он снимает любое подтверждение для пути через `memory/` рабочей папки:

- собственное правило пользователя «спрашивать» (`permissions.ask`) для папки внутри памяти: по настоящему пути Claude Code спросил, по пути через `memory/` файл записан без вопроса (`rt1-live-memory-ask-rule-acceptEdits.txt`);
- встроенное подтверждение Claude Code для особых имён: `.git/hooks/…`, `.claude/…`, `.bashrc` внутри памяти. По настоящему пути — запрос «sensitive file», по пути через `memory/` — записано без вопроса (`rt1-live-memory-protected-names-acceptEdits.txt`). Контроль: с `IWE_MEMORY_WRITE_AUTO_APPROVE=0` все шесть записей остаются с запросом (`…-control-hook-off.txt`), то есть вопрос снимает именно хук.

Правило «запретить» (`deny`) хук не обходит. Запись вне памяти, чужой проект, `..`, ссылки наружу, обычный режим и режим плана подтверждение сохраняют (ниже).

Чем опасно: в стандартной установке папка памяти не git-репозиторий и `.claude` оттуда не читается, поэтому до выполнения кода дело не доходит. У пользователя, который ведёт память под git, агент в `acceptEdits` после вредной подсказки запишет git-хук без подтверждения. Журнал изменений об этом ограничении молчит, а заголовок хука называет его безопасным («the hook stays silent») — это неверно.

Что нужно: хуку молчать, если в пути внутри памяти есть компонент, начинающийся с точки (или хотя бы `.git`, `.claude` и файлы настройки оболочки); правила `ask` хук увидеть не может — это назвать в журнале изменений и в анонсе. Исполняемая проверка: `probes/redteam/prompts/l1c-protected-names.txt` и `l2-ask-rule.txt` через `live.sh`; на кандидате запись проходит, после правки должна остаться с запросом. Владелец: платформа. Уверенность высокая. Опровергло бы находку: тот же запуск, где запись по настоящему пути тоже проходит без вопроса.

### Н2. Средняя, новое в rc.2. Исключение для личного репозитория судит только свой фрагмент команды (#1671, обращение #1658)

Случай Аудитора кода подтверждён и расширен. Сессия не открыта, каждая команда ниже проходит проверку, и после настоящего выполнения в одноразовой установке коммит оказывается в репозитории управления IWE (`rt3-session-gate-direct-rc2.txt`; `L` — личный репозиторий вне IWE без remote, `DS` — репозиторий IWE):

| Приём | Команда |
|---|---|
| переменные заданы раньше в цепочке | `export GIT_DIR=DS/.git GIT_WORK_TREE=DS; git -C L commit …` — также через `&&`, на предыдущей строке, внутри `( … )`, `declare -x`, присвоение и затем `export GIT_DIR GIT_WORK_TREE` |
| функция с именем git | `git() { command git -C DS "${@:3}"; }; git -C L commit …` |
| относительный путь | текущая папка агента — `L`; `cd DS && git -C . commit …`, то же с `pushd` — хук разрешает `.` от папки до команды |
| кавычки внутри пути | `git -C <родитель>/ws"/"DS-strategy commit …` при существующей рядом папке `ws"` — хук снимает только внешние кавычки, оболочка все |
| хвост цепочки | `git -C L commit …; env git commit …` — первая часть исключена, вторая не распознана |

Смена `PATH` раньше в цепочке тоже проходит (в пробе подставного git не было, коммит ушёл в `L`).

Что исключение держит: `push`; репозиторий с remote; worktree репозитория IWE вне папки; ссылку и файл `.git`, ведущие в IWE; `core.worktree`; другой регистр букв пути; `--git-dir`, `--work-tree`, `-c`, два `-C`; `GIT_DIR=` прямо перед командой; `set -a`; переменную, `$(…)` и обратные кавычки в пути; смешанную цепочку с распознанным коммитом в IWE.

Итог счёта: из 60 команд кандидат пропускает 35, выпуск 0.42.1 — 23; новых из-за rc.2 — 12. Журнал изменений обещает, что `GIT_*` в команде никогда не исключаются, — для цепочки это неверно. Что нужно в rc.3: исключение действует, только если вся команда — один `git -C <абсолютный путь> commit` без других команд, без кавычек внутри пути и без относительного пути. Исполняемая проверка: `probes/redteam/probe-session-gate.sh <установка> <метка>` — строка «total» должна совпасть с 0.42.1. Владелец: платформа. Уверенность высокая.

### Н4. Низкая, новое в rc.2. Слияние настроек после «y» называет себя «только добавляет», но может заменить значение пользователя

Сообщение и журнал изменений: «ваши значения не заменяются». Пользователь сузил охват платформенного хука (`secret-file-read-block.sh`: `Read` вместо `Read|Edit|MultiEdit|Grep`) и дал ему свой `timeout` — после «y» запись заменена записью шаблона, охват снова широкий, `timeout` пропал; конфликтом это не считается (`rt4-y-narrowed.txt`). Платформенный хук, удалённый пользователем намеренно, возвращается (`rt4-y-removed.txt`). Оба случая в сторону большей защиты, резервная копия прежнего файла остаётся в `.backups/settings-merge/`. Нужно поправить текст обещания либо считать сужение охвата конфликтом.

Что слияние держит: `--check` и ответ «n» файл не меняют и предпросмотр не пишут; битый JSON — файл не тронут, сказано почему; ссылка вместо файла — ссылка сохранена, обновлён файл, на который она ведёт; режим `rw-------` и свой ключ окружения сохранены, копия тоже `rw-------`; чужой тип значения — конфликт, только предпросмотр; после слияния JSON разбирается, временных файлов не остаётся.

### Н6. Низкая, новое в rc.2. В Kimi Code путь берётся не из того поля, что читает инструмент

Для инструментов Kimi (`ReadFile` и другие) защита секретов смотрит сначала `file_path`, потом `path`, а Kimi читает `path`. Запрос с `file_path` = обычный файл и `path` = `.env` хук пропускает (`rt2-secret-hook-direct-rc2.txt`). Сработает ли это в настоящем Kimi Code (примет ли он лишнее поле), не проверено. Для имён инструментов Kimi первым должно идти `path`.

### К сведению

- Обработчик памяти, прямые запросы (53, `rt1-memory-hook-direct.txt`): два ответа «разрешить» сверх ожидаемого. Кольцо ссылок — запись всё равно падает с ELOOP. Путь `memory/link-in/../x.md`, где текстовое и настоящее прочтение `..` расходятся, — в живом запуске Claude Code сам приводит путь и отказывается писать по ссылке (`rt1-live-memory-paths-acceptEdits.txt`), обхода нет.
- Хук доверяет переменным `CLAUDE_CONFIG_DIR` и `CLAUDE_CODE_PROJECT_DIR_NAME`: с ними чужой проект получает «разрешить» для памяти другого проекта и для папки вне памяти. Задать их может только тот, кто уже управляет окружением сессии.
- Выключатель срабатывает только на значение `0`; `false` и пустая строка хук не выключают.
- Подмена ссылки `memory` между ответом хука и записью — известное ограничение из заголовка хука, показано в пробе.
- Четыре запуска обновления из двенадцати остановились на сети: превышение 20 секунд на файл и исчерпанный лимит анонимных запросов к GitHub (60 в час). Обновление каждый раз отказалось целиком, ничего не изменив (`rt4-*-timeout.txt`, `rt4-y-readonly.txt`).
